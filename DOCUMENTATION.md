# Gudanah ATS Match Checker — Project Documentation

## What this is
A free, single-page tool: paste a job description and a resume, get an ATS-style
keyword match score plus a list of missing keywords to add. Hosted at gudanah.com,
which already gets recruiter/HR traffic (visitors arrive from the CV link) — this
tool is built to convert that existing traffic, not to chase new traffic.

## Why this idea (vs. the CRM)
The CRM idea was scrapped because it needed two expensive things: ESP/domain
approval (slow, gated by third parties) and a training dataset (none available).
This tool needs neither:
- No external API, no ML model, no training data — matching is done with
  keyword frequency + weighting, computed entirely in JavaScript.
- No backend, so no server cost and nothing to get "approved" before launch.
- No login, so zero friction between a visitor and their first result.

## How it works (algorithm, in plain terms)
1. Normalize both texts (lowercase, strip punctuation except things like
   `c++`, `node.js`, `c#`).
2. Extract candidate keywords from the job description: single words and
   two-word phrases (e.g. "project management"), filtered against a
   stopword list and a job-posting filler list ("responsibilities",
   "excellent", "strong", etc.).
3. Weight candidates higher if they appear more than once, or if they match
   a bundled list of common hard/soft skill terms (a small hardcoded array
   shipped in the code — not a fetched or trained dataset).
4. Take the top-weighted ~25 keywords as the "important" list for that JD.
5. Check each one against the resume text (exact match, plus light suffix
   stemming so "managing"/"managed"/"manages" all count as "manage").
6. Score = matched / total important keywords, as a percentage.
7. Show matched keywords, missing keywords (ranked by importance, most
   critical gaps first), and the score.

## Privacy stance (also a selling point)
By default, resume/JD text is never uploaded — the keyword match check
runs entirely in the visitor's browser. The one deliberate exception is
the optional AI Verdict feature (see below): when a user clicks that
button, the extracted resume + JD text is sent to a proxy and on to
Google's Gemini API to generate a summary. This is disclosed on the button
itself, not buried — the keyword checker's core promise ("your resume and
JD never leave your browser") stays true unless the user explicitly opts
into the AI feature. The one other network call the page makes is a
visit-counter ping on load (see GUIDELINES.md's second sanctioned
exception) — it carries no resume/JD text and no per-visitor identifier,
just an anonymous shared increment, so it doesn't compromise this promise.

## AI Verdict feature (sanctioned exception to "no backend")
Recruiters can click "Get AI verdict" to receive a short, structured
summary (fit level, top strengths, top gaps, one-line recommendation)
generated by an LLM, grounded in the tool's own computed score/keywords
(not a free-associated opinion — the prompt is fed our real analysis so
the output stays consistent with the keyword results shown on screen).

This required one deliberate exception to "no backend": an LLM API key
cannot live in client-side JS (anyone can read it via dev tools and drain
the account), so a minimal serverless proxy holds the key and forwards
the request. Scope of the exception, kept as narrow as possible:
- **Provider:** Google Gemini Flash (free tier — chosen specifically to
  keep this at $0; see GUIDELINES.md for the account setup this requires).
- **Proxy:** a single Cloudflare Worker (free tier, no cost). Stateless —
  it forwards a request and returns a response. No database, no logging
  of request bodies, no stored data.
- **What it is not:** this is not a general backend. It does not gain new
  responsibilities beyond "hold the Gemini key and relay one request type."
  Any new feature that would add a second responsibility to this proxy
  needs its own explicit sign-off, same as this one did.

## Tech stack
- Plain HTML/CSS/JavaScript. No framework, no build step, no npm install.
- `pdf.js` (CDN) for client-side PDF text extraction — the uploaded file
  is read locally via the File API and never leaves the browser; only the
  extracted text is used (and only sent onward if AI Verdict is clicked).
- Cloudflare Worker (`worker/index.js`) — the AI Verdict exception above.
  Free tier, deployed separately from the static site.
- `site-worker.js` — the second sanctioned exception (see GUIDELINES.md):
  serves `/api/visits` (Workers KV counter) and falls through to static
  assets for everything else.
- Deploy target: live at gudanah.com via a Cloudflare Worker
  (`gudanahats`) serving `public/` as static assets — see `deploy.sh` and
  the "Deploying" section in `README.md`. Not Cloudflare Pages: the
  domain's DNS was already a Workers Custom Domain binding before deploy,
  pointing at a placeholder Worker, so deploying our static assets to that
  same Worker name was simpler than migrating the DNS to Pages.

## Site structure: gudanah.com is a hub, this is the first tool
gudanah.com is meant to host more than one free tool over time, each
monetized the same way (Google AdSense once approved) and each following
the same build constraints in GUIDELINES.md. This repo currently contains
exactly one tool, living at the site root (`/`) so the existing SEO/URL
recruiters already reach isn't disturbed.

**Adding a new tool later:**
1. Build it at `public/<tool-slug>/index.html` (its own self-contained
   HTML/CSS/JS — no shared framework, per GUIDELINES.md #6).
2. Copy the `<header class="site-header">` block from this `index.html`
   into the new page, and add one `<li>` for the new tool.
3. Add that same `<li>` to *every other* tool page's header (including
   this one) so the nav stays in sync. There's no shared include/template
   — that's a deliberate zero-build tradeoff, not an oversight.
4. Add the new URL to `public/sitemap.xml`.

## SEO
Done now (no domain-live dependency, safe to build ahead):
- Real `<title>` and meta description targeting the actual search intent
  ("free ATS resume checker"), not generic placeholder copy.
- Canonical tag, Open Graph + Twitter card tags, and a WebApplication
  JSON-LD block so search engines and link previews understand the page.
- `robots.txt` and `sitemap.xml` at the site root, pointing at
  `gudanah.com` (the intended production domain, chosen ahead of time so
  these files don't need editing again at launch).

Deliberately deferred until the domain is actually live and pointed at
the deployed site:
- **Google Search Console verification** — this requires proving domain
  ownership (a DNS TXT record or a file upload to the live site), tied to
  your own Google account. Same category as the Gemini API key: an
  account/ownership step only you can do, not something to hand an agent.
- **Submitting the sitemap** in Search Console, which only works once the
  domain resolves to the deployed site.
- Any backlink/content-marketing work — out of scope for a code build,
  and not worth planning before the site is live and has a real URL to
  point people to.

## MVP scope (v1 — build now)
- Paste JD + paste resume, OR upload a resume PDF (parsed client-side) →
  score + matched/missing keyword lists.
- Daily free-scan counter (soft cap, stored in localStorage) — this is the
  freemium *mechanism*, wired up now even though no real paywall exists yet.
- Optional "Get AI verdict" button (see above) — clearly marked as sending
  data to an external AI service, off by default (never auto-triggered).
- A clearly labeled placeholder ad slot in the layout (empty div, no ad
  network script) — reserves the space so wiring in AdSense later is a
  one-line change, not a redesign.
- Responsive, accessible (color is never the only signal — score bands are
  labeled in text too).

## Phase 2 (explicitly deferred — do not build until v1 is validated)
- Real AdSense integration (requires their review process).
- Real payment wiring for a paywall past the free daily cap (Stripe),
  including gating the AI Verdict feature once Gemini free-tier limits
  are a real constraint.
- Any analytics (only after deciding on a privacy-respecting option —
  don't undercut the "nothing leaves your browser" pitch).

## Non-goals
- No AI/LLM calls from the keyword-matching core — AI is opt-in, additive,
  and isolated to the one proxy described above.
- No accounts, no email capture, no login, on the site itself.
- No data storage anywhere, including in the proxy.
